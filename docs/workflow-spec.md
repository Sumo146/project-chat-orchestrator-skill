# project-chat-orchestrator工作流说明

本文解释工作对象和设计关系，具体触发、任务包、模型建议、禁止项及操作顺序以[现行Skill](../skill/project-chat-orchestrator/SKILL.md)为准。本文不是第二份运行指令，历史试验结果见[测试记录](test-plan.md)

## 项目与对话

| 对象 | 含义 |
|---|---|
| Codex项目 | 侧边栏中的本地项目容器，例如绑定`E:/Codex_Project/Test`的`Test` |
| 逻辑项目 | 工作区内的独立项目目录，例如本项目`20260807-project-chat-orchestrator-skill` |
| 项目文件范围 | 本次任务实际可使用的文件和路径，可以是一个目录，也可以是分散的多个路径 |

一个Codex项目可以包含多个逻辑项目。Skill要求主控和它创建的普通执行对话属于同一个Codex项目，并共同使用已确认的项目文件范围；各执行对话只获得完成自身任务所需的路径子集。不能把工作区根目录自动当成本次任务的全部授权范围

这些对话在侧边栏平级显示，不形成界面上的父子树。主控按稳定对话ID分配和追踪工作；标题只方便识别，用户改名不改变对话身份。它们是普通对话，不是Subagents

## 角色与分工

| 角色 | 建议职责 | 创建条件 |
|---|---|---|
| `C00`主控 | 与用户确认方案、分配任务、检查、返工和汇总 | 当前主对话 |
| `E01`至`E0N` | 完成已分配的实施工作 | 根据可独立验收的任务创建 |
| `R01` | 独立审查，默认只读 | 风险较高或用户要求时 |
| `D01` | 研究复杂方案，默认不改实现文件 | 方案需要单独讨论时 |

主控给出数量、角色、职责、模型、推理等级和并发建议，用户决定最终安排。同一文件、共享配置或公共文档不交给多个并行写入对话；不能消除冲突时采用串行批次或单一文件负责人

用户可以直接参与某个子对话。子对话收到职责外要求时先说明范围、路径、冲突和验收变化，取得单独确认后再执行。若新职责占用其他对话的文件，子对话在自身对话记录改派需求并暂停，主控读取后协调原负责人和更新任务包

## 确认与编排模式

用户明确调用Skill或要求当前对话管理其他普通对话时，主控进入编排模式。已分配给执行对话的实现工作仍由其负责；继续、开始执行等短指令续接现有计划，不自动授权主控实施。只有用户明确改派具体任务，主控才接手该项

新建对话前，主控在一份计划中确认任务归属、路径权限、依赖、验收、并发、每个新对话的具体模型和推理等级。已有对话继续按稳定ID接收任务，用户手动修改的标题、模型和推理等级不被后续消息覆盖。计划确认后，分发是第一个业务动作；分发失败保留阻塞状态，不转由主控自行实现

项目范围分别标注协调目录、默认工作目录、读写、只读和排除路径。所需路径不可访问时由用户选择调整，不能假定子对话具备权限。默认共享项目目录，只有用户明确要求隔离开发时才使用worktree

## 通信与等待

子对话把进度、结果、风险和待确认问题留在自身对话，不主动向主控发送消息或通知，也不唤醒、切换、导航到主控。审查和方案讨论对话同样遵守这一方向

主控分发后默认进行一次即时或短时状态检查，记录结果后结束当前运行。用户明确要求持续等待时，主控可主动等待、读取和汇总，并说明这会占用当前主控运行。主控发送补充或返工后也按用户选定的等待方式处理；子对话的完成事件不代替主控主动读取

主控用稳定对话ID读取状态、发送返工并汇总。项目或阶段完成后保留普通对话，不自动归档、隐藏、重命名或删除
